Start here / conveniences before machinery

Find your first call.

One codec, a set of codecs, or a configured job. Open the code above and below each call to see its complete, compiled context.

Bring the concrete codec crate for each format you register. zencodec supplies traits and CodecSet; pixel views come from zenpixels. zencodec::prelude::* imports the common encode/decode traits. These examples use explicit imports so you can see exactly which trait enables each method.

Repository main includes unpublished interfaces. Native QOI and BMP are small lossless fixtures for the examples. Use the codecs your application needs; this is not a browser-format selection. zencodec-io drivers come later, when bytes stop being a resident slice.

A different question / when to wait

A small output queue can pin a large image.

Byte availability and storage release are different contracts. CPU fairness remains useful in both paths.

Qualify the configuration. Couple encoding to a slow writer only when raw/intermediate storage is bounded and the upstream can pause. Otherwise, finish and release into independently admitted encoded storage; cap staging and concurrent jobs. A caller-owned full raster still counts. A memory cap may require refusal; it does not guarantee successful bounded completion.

The friction / keep it visible

Complexity has to earn its place.

These steps still need a better contract or more evidence. The guide links the open design question at the point it becomes relevant.

A nostdio-style Read/Seek adapter can help an existing synchronous parser. It does not supply suspension, all-required range plans, immutable object identity, or shared storage admission. Keep that bridge narrow; the current evidence does not justify a second core I/O hierarchy.
